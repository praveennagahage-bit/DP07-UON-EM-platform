# 老师反馈：下一阶段计划（2026-10-16）

状态：仅记录需求，以下四项尚未在本轮实现。来源为项目负责人转述的老师建议；“建议细节”是后续实现设计，不代表老师已确认。

## 1. 通过 AI API 审核活动内容

- [ ] 接入 AI 内容审核 API，辅助识别敏感或有害活动内容，而不只依靠关键词。
- [ ] 创建和编辑活动均在后端审核，向用户说明审核结果。
- [ ] 明确与现有关键词名单、用户举报和管理员处理的关系。

建议细节：先覆盖标题、描述和地点；API 密钥仅保存在后端配置，不进入前端或 Git。明确误判复核、超时/服务不可用处理以及费用控制。待确定服务商、预算、审核类别、拦截阈值和是否覆盖图片。本次不选择服务商、不申请密钥、不调用外部服务。

## 2. 网站统计面板

- [ ] 新增统计面板，展示网站数据，例如用户人数。

建议首版指标：用户总数及角色分布、有效/封禁账号数、活动总数、未来/已开始/已取消活动数、当前报名总数、待处理举报数。所有数字来自真实数据库，明确统计口径，避免将报名次数当成独立人数。
待确定：Admin 查看全站数据；是否另外提供 Organizer 仅查看自己活动的统计。时间按 Australia/Sydney，取消状态与时间分类需清晰。

## 3. Admin / Organizer 主动发送站内消息

- [ ] Admin 和 Organizer 能主动给相应用户或 Organizer 发消息。
- [ ] 收件人在现有 Notifications / 铃铛中查看消息。
- [ ] 支持活动提醒场景，例如提醒参加者携带饮用水。

建议权限边界：Admin 可给选定用户、Organizer 或某场活动的报名者发送；Organizer 默认只给自己活动的报名者发送，不能借此获取全站用户名单。老师提出的“给 Organizer 发消息”需要后续明确 Organizer 之间是否允许互发及范围，暂不视为已批准的全站广播权限。
建议消息包含发送者、标题、正文、发送时间及可选活动链接；单次收件人去重，限制长度和发送频率，保留发送记录，并复用未读/已读机制。待确定单发、群发及回复功能；这次只记录站内通知，不包括邮件或即时聊天。

## 4. 管理页面按钮布局

- [ ] Users 卡片中 Grant/Revoke admin access、Suspend/Restore account 等按钮有一致间距。
- [ ] 同一卡片内按钮宽度一致，卡片之间布局协调。
- [ ] 检查长按钮文字、只有一个按钮的 Admin 卡片和手机宽度下的布局。

依据：用户提供的截图中授权和封禁按钮上下贴在一起，宽度不同。建议使用统一操作区、固定 gap 和一致宽度规则；不修改权限逻辑。
