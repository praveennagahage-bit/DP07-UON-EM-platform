# Demo 后老师反馈：下一阶段待办

本文件记录用户转述的老师反馈及建议实现方式，尚未表示这些功能已经完成。此次只记录，不开始实现。

## 1. 活动输入限制与合法性校验

- [ ] 创建、编辑活动的标题上限改为 15 个字。
- [ ] 描述限制在约 500 字。
- [ ] 检测脚本、HTML 等不符合普通文本要求的输入。
- [ ] Location、Capacity 等字段增加合理性校验；前后端规则一致。

待确认：英文的“15 个字 / 500 字”是字符还是单词；中文、空格和标点如何计数。描述的精确上限也需确认。不要直接截断已有活动内容。

建议：拒绝空白标题和地点、设置地点长度上限；容量必须是有合理上限的正整数，不能小于已报名人数。地点只填数字（截图中为 1、2）是否禁止，应考虑真实房间号等使用场景后制定规则。

安全实现：将内容始终作为普通文本显示，避免执行用户提供的 HTML 或脚本；数据库继续使用参数化查询。不能只凭 JavaScript、引号或尖括号等关键词判断恶意输入，否则会误伤编程课程标题和正常标点。输入规则不替代输出安全处理。

## 2. Profile

- [ ] 实现 /profile 页面，修复 View Profile / Update Profile 的无效入口。
- [ ] 查看当前账号资料，修改允许编辑的字段并保存。
- [ ] 后端根据登录会话限制只能修改自己的资料。

建议第一版：姓名可编辑，邮箱和角色先只读；头像和简介作为可选扩展。具体可编辑字段待确定。不需要每个账号单独建数据库，可复用 users 表，必要时添加字段或使用 userId 关联资料表。角色不能通过个人资料接口自行提升。

## 3. 活动卡片布局

- [ ] 首页 Upcoming Events 和 Events 列表统一卡片布局，View Details 按钮底部对齐。
- [ ] 过长标题、描述、地点限制展示行数并用省略号表示；详情页保留完整内容。
- [ ] 处理无空格长字符串、缺少图片、长地点等情况。

截图中首页卡片高度差异主要来自标题和地点换行，不仅是描述。建议卡片内容区使用弹性布局，按钮推到底部，文字使用多行截断，避免单纯硬裁剪内容。

## 4. 手机显示与操作

- [ ] 检查首页、活动列表/详情、创建/编辑、登录、报名、通知和 Profile 的手机布局。
- [ ] 检查导航、侧栏、表单、图片、表格是否溢出，避免横向滚动。
- [ ] 检查触摸操作、时间选择器、文件上传及虚拟键盘对布局的影响。
- [ ] 至少覆盖约 360、390、430 像素宽度；有条件时用真实手机补充验证。

## 5. Admin / Administration

用户理解：老师希望有独立的全站管理员账号，能封禁用户、处理不当活动，并拥有跨 Organizer 的编辑和删除权限。具体管理流程仍待进一步明确。

| 角色 | 权限范围 |
| --- | --- |
| Attendee | 浏览活动、报名/取消自己的报名、个人通知和资料 |
| Organizer | 创建活动、只编辑和管理自己的活动及参加者 |
| Admin | 全站账户与活动管理，处理违规用户和活动 |

- [ ] 新增独立 admin 角色及管理页面，后端检查管理权限。
- [ ] 提供用户列表、封禁/解封；封禁应同时使已有会话失效并阻止重新登录。
- [ ] 全站查看、编辑、下架或删除不当活动；保留 Organizer 的所有权限制。
- [ ] 管理操作记录操作者、时间、目标和原因。
- [ ] Admin 账号通过受控方式创建，不能开放公众注册选择或个人资料提权。

待决定：有报名者的活动被处理时，是下架/取消并通知参加者，还是允许永久删除；如何保留报名与通知历史；是否允许管理员封禁其他管理员、如何避免锁死唯一管理员。首版建议优先可追溯的下架/取消流程。

## 建议实施顺序（非老师指定）

1. 确认字数口径，完成输入校验和卡片布局。
2. 完成基础 Profile。
3. 实现 Admin 权限、账号状态和活动管理流程。
4. 对全部页面做手机端回归检查；各功能开发时同步考虑移动布局。

每轮完成后运行对应检查，上传前获取远端更新、处理冲突，保留真实开发提交。
